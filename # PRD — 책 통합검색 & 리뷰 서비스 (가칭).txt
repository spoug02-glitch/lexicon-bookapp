# PRD — 책 통합검색 & 리뷰 서비스 (가칭)

---

## SECTION 1. 제품 한줄 설명

책을 어디서 구할지(도서관 대출/구독앱/구매/중고) 고민하는 독서가를 위해, 소장·구독 여부를 한 번에 검색하고 획득 경로와 무관하게 리뷰를 한곳에 모을 수 있는 통합 서비스.

---

## SECTION 2. 문제 정의 & 목표 설정

**현재 문제**

서울시 구립도서관은 시스템이 구별로 제각각이라 특정 책의 소장 여부를 확인하려면 여러 사이트를 돌아다녀야 한다... 민간 전자책 구독앱(리디셀렉트/밀리의서재/윌라)도 사정은 비슷해서, 원하는 책이 어느 앱에 있는지 미리 알기 어렵다.

이 "책이 있는지 없는지"는 단순한 불편이 아니라 실제 구독 선택·해지의 이유로 작동한다... 예를 들어 한 블로거는 리디셀렉트에 원하는 책이 부족해 2019년 11월 밀리의서재로 완전히 갈아탔다고 밝혔고(WORLD OF YuReKa 블로그), 여러 독립 블로거가 "책 보유 여부"를 구독앱 비교표의 정식 항목으로 다루고 있다(컴모아 블로그 등).

리뷰 쪽 문제는 또 다르다... 알라딘 리뷰는 알라딘에서 산 책에, 밀리의서재 리뷰는 밀리 안에서 읽은 책에 묶여 있어서, 도서관에서 빌린 책은 리뷰 남길 곳이 마땅치 않다. 그 결과 노션·블로그·카페에 따로 기록하게 되는데, 이렇게 흩어진 기록은 다음 검색에 재사용되지 않는다.

여기에 피클플러스 같은 공동구독 플랫폼을 이용하는 경우, 계정을 공유하다 보니 "내 독서 기록이 온전히 내 것으로 남지 않는" 문제도 겹친다(관련 언급: 블로그 van2bam, 2025.11.07 — "계정 공유가 불편하거나 가족끼리 따로 독서 데이터를 관리하고 싶은 분들").

이 지점은 Claude in Chrome을 이용해 국내 독서기록 앱 10종(리더스, 북플립, 산책, 리딩트리, 북덕방, 북적북적, 북슐랭, 사락, 그믐, 플라이북)을 직접 조사해 재확인했다... 10개 앱 모두 책 등록 시 "어느 플랫폼(리디/밀리/윌라 등)에서 읽었는지"를 선택하는 표준 필드는 제공하지 않았고, 있어도 태그나 서가 이름으로 수동 분류하는 수준에 그쳤다(조사 근거: 각 앱 App Store/Google Play 공식 설명 및 업데이트 히스토리). 단, 이 조사는 스토어 설명·리뷰 기반이며 실제 앱을 설치해 등록 화면까지 확인한 건 아니라는 점은 한계로 남는다.

해외 대표 서비스인 굿리즈와 스토리그래프도 같은 패턴을 보였다. 굿리즈는 플랫폼 전용 필드 없이, 사용자가 직접 만드는 커스텀/exclusive 책장(shelf)으로 우회하는 구조다(근거: Goodreads 공식 고객센터 문서). 스토리그래프는 "에디션(Kindle Edition, Audio Edition 등)"을 전환하는 방식과 커스텀 태그로 처리하는데, 운영진이 공식 포럼에서 "전자책 에디션을 'kobo'나 'kindle' 태그로 구분해서 쓰는 경우가 많다"고 직접 답변했다(근거: StoryGraph 공식 로드맵 포럼). 즉 국내외를 막론하고 "플랫폼을 지정하는 전용 필드"는 업계 표준이 아니며, 있어도 사용자가 태그·책장을 직접 만들어 우회하는 방식이 일반적이다.

**문제의 결과**

- 책 하나를 두고 도서관/구독앱/구매/중고 중 뭐가 나은지 판단하려면 여러 서비스를 개별적으로 확인해야 함
- 리뷰가 플랫폼별·계정별로 흩어져서 "내가 남긴 리뷰"를 한눈에 모아볼 수 없음
- 기존 서점형 가격비교 앱(북프라이스, 책거리)은 이미 존재하지만 커버리지가 서점에 한정돼 있고, 이용자 후기에서도 "커버리지가 부족하다"는 불만이 확인됨(책거리 앱 리뷰)
- 기존 독서 기록/커뮤니티 앱(그믐, 플라이북, 리더스)은 기록·커뮤니티 기능은 있으나 "이 책을 어디서 구했는지"는 다루지 않음

**서비스 목표**

책 검색 한 번으로 소장·구독·구매·중고 현황을 비교하고, 어디서 읽었든 리뷰가 한곳에 쌓여 다음 사람의 검색에 다시 도움이 되는 순환 구조를 만든다.

## SECTION 3. 타깃 사용자 & 시나리오

**대표 페르소나**

책을 자주 사거나 빌려 읽는 20~30대 독서가... 도서관, 구독앱, 서점, 중고거래를 상황에 따라 섞어 쓰며, 읽은 책을 기록으로 남기고 싶어 하지만 기록이 여러 곳에 흩어져 있는 것에 답답함을 느낀다.

**시나리오 1 — 획득 경로 결정**

읽고 싶은 책이 생겼다... 새로 구독앱을 하나 더 늘릴지, 우리 동네 도서관에서 빌릴지, 아니면 그냥 살지 판단이 서지 않는다. 앱에서 책 제목을 검색하면 도서관 소장 여부, 구독앱 포함 여부(확인 가능한 범위), 최저가 구매처, 중고 시세가 한 화면에 뜬다.

**시나리오 2 — 리뷰 기록**

도서관에서 빌린 책을 다 읽었다... 예전 같으면 노션이나 블로그에 따로 적었겠지만, 이번엔 앱에서 그 책을 찾아 리뷰를 남긴다. 나중에 이 책을 검색하는 다른 사람에게 "도서관에서 봤다"는 경로 정보와 함께 리뷰가 노출된다.

## SECTION 4. 핵심 기능 리스트

| 기능명 | 설명 | 우선순위 |
|---|---|---|
| 도서관 소장 검색 | 도서관정보나루 API 기반, 구별 공공도서관 소장/대출 가능 여부 조회 | MVP |
| 서점 가격/중고 검색 | 알라딘 Open API 기반 정가·중고 매장 검색 (일 5,000회 호출 제한, 개인계정 사용 범위 내) | MVP |
| 책 상세 페이지 | 도서관/서점/중고 정보를 한 화면에 통합 표시 | MVP |
| UGC 리뷰 작성 | 획득 경로 2단 선택으로 리뷰 작성. 1차: 도서관/구독/온라인/오프라인. 구독·온라인 선택 시 2차로 세부 플랫폼(예: 밀리의서재, 리디셀렉트, YES24, 알라딘 등)을 프리셋+자유입력(자동완성)으로 선택. 온보딩 없이 매번 자유 선택 방식(사용자가 서비스를 자주 옮겨 다니는 점 반영). 신품/중고 축은 다루지 않음(중요도 낮다고 판단) | MVP |
| 리뷰 피드 | 내가 쓴 리뷰를 경로 무관하게 한곳에서 모아보기 | MVP |
| 구독앱(리디/밀리/윌라) 포함 여부 | 공식 API 부재로 수동 확인이나 사용자 제보 방식 검토 필요 | Later |
| 개인간 거래(당근/번개/중고나라) 통합 | 공식 API 없음, 크롤링은 약관 위반 리스크 있어 보류 | Later |
| 리뷰 기반 추천 | 축적된 리뷰 데이터로 "어디서 읽는 게 나은지" 추천 로직 | Later |
| 웹소설 구간별 경로 기록 | 한 작품 안에서 화수 구간별로 경로가 다른 경우(예: 1~50화 리디, 51~100화 카카오페이지)를 기록하는 기능. 리뷰 1개당 경로 1개인 현재 데이터 모델로는 표현 불가 — 관계형 하위 테이블 설계 필요, MVP 범위 밖 | Later |

---

## SECTION 5. 사용자 플로우 (성공 케이스)

1. 앱 실행 후 책 제목 검색
2. 도서관 소장 여부, 서점 정가, 중고 시세가 한 화면에 표시됨
3. 사용자가 "도서관에서 빌리기"를 선택하고 실제로 대출
4. 다 읽은 후 앱으로 돌아와 리뷰 작성, 획득 경로 1차("도서관")를 함께 기록 (구독/온라인 선택 시에는 2차로 세부 플랫폼까지 선택)
5. 작성한 리뷰가 내 리뷰 피드와 해당 책 상세 페이지에 동시에 노출

---

## SECTION 6. 비기능 요구사항

- **플랫폼**: 모바일 웹 또는 앱 (미정, 별도 결정 필요)
- **로그인**: 리뷰 작성·피드 기능을 위해 필요 (소셜 로그인 검토)
- **언어**: 한국어 단일 지원
- **데이터 소스**: 도서관정보나루 API, 알라딘 Open API — 둘 다 공식 API로 약관상 사용 가능. 리디셀렉트/밀리의서재/윌라, 당근마켓/번개장터/중고나라는 공식 API가 없어 MVP 범위에서 제외
- **API 제약**: 알라딘 개인 계정 API는 일 5,000회 호출 제한, 대량/기관용은 법인 명의 필요(알라딘 API 정책)
- **획득 경로 데이터 구조**: 1차 대분류(도서관/구독/온라인/오프라인, 고정값) + 2차 세부 플랫폼(구독·온라인 선택 시에만 노출, 프리셋 목록 + 자유입력 자동완성). 온보딩 단계에서 서비스를 미리 등록하는 방식은 채택하지 않음 — 사용자가 구독·구매처를 자주 바꾸는 경향을 반영. 신품/중고 구분은 다루지 않음
- **노션 호환**: 위 구조를 노션 데이터베이스로 옮길 경우 1차 경로는 Select, 2차 세부 플랫폼은 Select 또는 Multi-select 속성으로 매핑 가능하도록 값 목록을 명확히 관리할 것

---

## SECTION 7. 성공 지표

- 책 상세 페이지에서 리뷰 작성으로 이어지는 전환율
- 한 사용자가 남긴 리뷰 중 "도서관/구독/온라인/오프라인" 경로가 2개 이상 혼재된 사용자 비율 (여러 경로를 오가며 쓰는지 확인)
- 재방문 검색 횟수 (지난 대화에서 짚었듯, 책 검색은 구독 전 1회성 비교 패턴에 가까울 수 있어 이 지표로 리텐션 구조가 실제로 작동하는지 검증 필요)

## 미검증 리스크 (참고)

- **콜드스타트**: 그믐·플라이북·리더스 등 기존 UGC 독서 기록 앱도 겪고 있는 문제로, 리뷰가 쌓이기 전엔 앱의 매력이 낮음
- **재방문 빈도**: 키노라이츠(OTT)는 이미 여러 개 구독 중인 사람이 반복 검색하는 구조인데, 책 구독앱 동시 구독이 OTT만큼 흔한지는 근거 없음. 네이버 블로그/카페 검색에서 동시구독 사례는 확인되지만(예: 이북 리더스 카페, 니아걸 블로그), 비율은 확인 불가
- **구독앱/개인거래 통합**: 가장 차별화되는 부분이지만 공식 API가 없어 기술적으로 가장 리스크가 큼
- **플랫폼 선택 태그 기능**: 국내 독서기록 앱 10종 + 해외 대표 앱(굿리즈, 스토리그래프) 조사 결과 모두 전용 필드 없이 커스텀 태그/책장으로 우회하는 것으로 확인됨(굿리즈 공식 고객센터, 스토리그래프 공식 로드맵 포럼 근거). 다만 국내 조사는 스토어 설명 기반이라 실제 등록 화면까지 검증된 건 아님 — 필요시 앱 직접 설치 후 재확인 필요
